**项目名称**：面向麒麟操作系统的安全智能运维 Agent
**赛题编号**：中国软件杯 A2
**文档版本**：v1.1

---

## 1 引言

### 1.1 编写目的

本文档对「面向麒麟操作系统的安全智能运维 Agent」进行完整的功能与非功能需求分析，明确系统应当具备的能力、运行约束与验收标准，作为后续功能设计、编码实现与测试验收的统一依据。文档的预期读者为本系统的开发人员、测试人员与项目评审人员。

### 1.2 项目背景

在教育、医疗等行业的企业级数据中心，运维人员日常需要处理大量复杂的操作系统问题，例如僵尸进程堆积、磁盘 I/O 异常、日志文件撑满磁盘、关键配置文件漂移等。传统运维高度依赖人工编写的脚本与监控告警，使用门槛高、故障响应慢，对运维人员的经验提出了很高的要求。大语言模型的成熟使「用自然语言运维」成为可能，运维人员只需用日常语言描述意图，系统即可理解并完成相应操作。

然而，将大模型引入运维链路也带来了一个根本性的挑战，即人工智能推理过程的不可控性。模型可能在受到提示词注入诱导，或在自身产生幻觉的情况下，生成诸如删除根目录、篡改用户口令文件之类的灾难性指令。一旦这类指令被直接执行，后果不可逆转。因此，本项目要解决的核心命题，并不仅仅是「让人工智能能够对话运维」，而是「让人工智能的对话运维做到安全可控、全程可追溯」。围绕这一命题，安全护栏被确立为系统的核心，贯穿需求、设计、实现与测试的全过程。

为便于阅读，表 1.1 列出本文档中反复出现的专业术语及其含义。

| 术语 | 说明 |

## 2 项目概述

### 2.1 产品定位

本系统是一套部署在麒麟操作系统上、通过自然语言完成 Linux 运维的智能代理。系统采用浏览器与服务器（B/S）架构，运维人员在浏览器中以自然语言描述运维需求，系统随即感知操作系统的实时状态，进行推理决策，执行安全校验，在最小权限下完成操作，并将整个过程完整留痕。与同类对话式运维工具相比，本系统最突出的差异在于安全护栏：它不仅能够高效地理解并执行运维意图，更能够拦截误删数据库、危险命令注入等高风险操作，并产出可供事后追溯的思维链审计记录。

### 2.2 用户特征

系统主要面向三类相关方。第一类是运维管理员，是系统的主要使用者，通常为数据中心或服务器的运维人员，其核心诉求是用自然语言快速完成系统诊断与处置，同时要求每一步操作安全可控、有据可查。第二类是安全审计员，负责合规检查与事后追溯，其诉求是能够回放任意一次会话的完整推理链，据此确认系统未发生越权行为。第三类是潜在的攻击者，作为威胁来源，可能试图通过精心构造的对话内容诱导智能体越权执行；系统需要能够识别并拦截这类企图，攻击者本身不是系统的服务对象，而是安全需求的来源。

### 2.3 运行环境

系统的目标运行环境为采用 LoongArch 架构的麒麟高级服务器操作系统 V11。服务端基于 Python 3.11 与 FastAPI 框架构建，运维工具层依托 MCP 官方软件开发工具包实现，审计数据采用 SQLite 数据库存储。客户端为运行在现代浏览器中的单页应用，基于 Vue3 与 Element Plus 构建。大模型推理默认调用国产开源的 DeepSeek 云端接口，在离线或无网络环境下可切换至本地确定性桩以保证系统始终可演示。

### 2.4 设计约束

系统的设计与实现需遵守若干硬性约束。在架构上，系统必须采用 B/S 架构并部署于 LoongArch 架构的麒麟 V11 之上，并必须通过 MCP 协议对运维工具进行封装。在安全上，系统严禁在未经授权的情况下修改操作系统的关键配置文件，所有可变更命令的执行都必须经过统一的执行出口与安全护栏，不允许在程序的任何位置直接裸调系统调用接口。在技术选型上，系统优先采用国产软件与国产开源大模型，以契合国产化的总体要求。

## 3 功能需求

### 3.1 用例模型

系统的参与者与用例关系如图 2.1 所示。系统的主要参与者是运维管理员，由其发起自然语言运维对话、执行受控处置动作并查看审计回放。攻击者作为威胁主体，通过对话内容诱导智能体越权，相应的企图由系统的提示词注入防御与危险操作拦截等用例予以处置。此外，DeepSeek 大模型与麒麟操作系统作为外部参与者，分别参与系统的编排推理与状态感知。

### 3.2 关键用例描述

**自然语言运维对话**是系统最基础的用例，参与者为运维管理员，其前置条件是系统已启动且 MCP 工具与大模型均已就绪。该用例的主流程为：管理员输入自然语言运维指令后，系统首先对指令进行意图风险过滤与提示词注入体检，对其中的修改类意图再叠加一次基于语义的研判；随后大模型从只读 MCP 工具中选择合适的工具并采集系统状态，工具返回的不可信输出经隔离阅读处理后再回喂模型，模型据此给出运维结论；最终，本次会话的五段思维链被完整写入审计库。当指令被判定为破坏意图或命中注入特征时，系统在进入大模型之前即直接拒绝；当语义研判认定为高危时，系统拦截该请求并建议管理员改述。用例结束后，系统返回运维结论与一个会话标识，供后续回放使用。

**执行受控处置动作**用例用于完成对系统状态的实际变更，参与者同样为运维管理员，其前置条件是已通过对话或诊断定位到具体的可处置项。该用例的主流程为：管理员从白名单动作中选定一项并发起，系统强制要求二次确认，随后在动作层进行语义校验（如判断文件的关键性、识别受保护进程等），再由命令护栏进行规则校验与最小权限校验，最终在沙箱内以最小权限落地执行，并将五段思维链写入审计库。在此过程中，任一层校验未通过都会触发拦截；若管理员尚未完成二次确认，系统仅返回护栏的裁决预览而绝不执行。

**危险操作拦截**是上述两个用例的扩展。当对话或受控动作所产出的候选命令命中高危规则时（例如删除关键路径、磁盘格式化、未授权提权、外联反弹 shell 或命令注入等），系统在执行点触发拦截：对最高危等级的命令无条件拒绝，对中高危等级的命令则按授权状态与确认状态进行门控处置，并将拦截原因写入审计、向用户解释。

### 3.3 基本功能需求

系统应实现六项基本功能。

**操作系统环境深度感知（F1）**要求系统能够自动调用 `lsof`、`netstat`、`journalctl`、`df`、`ss` 等系统原生命令以及 `psutil` 库，获取进程、网络、日志、磁盘、句柄与系统等多维度的实时上下文。其验收标准是：系统能够列出全部感知工具，并通过调用工具取得真实的系统数据。

**运维插件化（F2）**要求系统采用插件化架构，将运维感知能力封装为大模型可调用的工具，并对工具进行统一注册与读写级别标注。其验收标准是：工具以 MCP 协议对外暴露，可被列举，也可被调用。

**安全意图校验（F3）**要求系统建立风险识别规则库，对落地命令进行独立的二次过滤，识别诸如危险的删除参数、不安全的权限修改等高危操作。其验收标准是：危险命令能够被拦截，并向用户解释拦截原因。

**最小权限代理执行（F4）**要求系统实现权限隔离，使核心运维动作在受限账户下运行，做到非必要不使用 root。其验收标准是：需要提权的操作在未获授权时能够被拦截。

**推理链路溯源（F5）**要求系统完整记录「接收指令、感知环境、推理决策、安全校验、执行结果」的闭环日志，支持异常情况下的回溯。其验收标准是：能够按会话标识回放整条推理链路。

**智能化根因分析（F6）**要求系统在磁盘占用过高时定位大文件并判断其关键性后给出建议，在出现僵尸进程时定位其父进程，并能够对系统负载、内存、I/O 与配置漂移等问题进行关联分析。其验收标准是：系统给出证据链与处置建议，但不自动执行任何变更。

## 4 非功能需求

### 4.1 确定性与可靠性

系统在确定性与可靠性方面有严格要求。系统严禁在未经授权的情况下修改操作系统的关键配置文件，例如用户口令文件、文件系统挂载表与 SSH 服务配置文件等。所有可变更命令都必须经过统一的执行器出口与安全护栏，护栏不放行则绝不执行。护栏规则支持热加载以便灵活调整，但其中的红线规则（即最高危且应当无条件拒绝的操作）以硬编码方式兜底，配置层无法将其削弱。当规则配置文件损坏时，系统采取故障安全策略，继续沿用上一份已生效的规则，从而保证护栏不会出现空窗。

### 4.2 抗注入能力

系统需具备较强的抗提示词注入能力。对于对话中出现的越权诱导话术，系统能够识别并拒绝，同时记录在案。对于隐藏在工具输出或文件内容中的注入指令，系统先以结构化标记的方式对其进行隔离与降权，再经由双模型隔离阅读处理，使原始的不可信字节始终不进入规划模型的上下文。在此之上，系统保持一项结构性不变量，即感知层的全部工具均为只读，因此即便注入在某一环节得逞，也无法升级为对系统状态的实际变更。

### 4.3 性能需求

系统需保证安全护栏不显著增加运维时延。安全护栏的单次裁决应处于亚毫秒量级，相对于一次完整运维操作可以忽略；用户感知到的端到端延迟主要由大模型的网络往返决定。审计数据的写入不得阻断主流程，应以异步方式进行，写入失败时仅作记录而不影响运维。

### 4.4 安全与权限

系统对自身的安全与权限管理同样有要求。改变系统状态的受控动作端点是唯一的状态变更入口，在生产环境中需经操作令牌鉴权后方可调用。系统默认仅监听本机回环地址，以缩小攻击面。审计数据在写入之前需对其中的凭据信息（包括令牌、密钥、口令与私钥等）做脱敏处理，避免敏感信息落盘。

### 4.5 国产化

系统在技术栈选择上贯彻国产化要求。大模型采用国产开源的 DeepSeek，后端框架、数据库与前端组件均优先选用国产或开源软件，整体部署目标为国产 LoongArch 架构与麒麟操作系统。

## 5 数据需求

系统的审计数据采用 SQLite 数据库存储，核心为会话表与思维段表两张表，二者通过会话标识建立一对多关联，并以基于哈希消息认证码的哈希链防止数据被篡改（详见功能设计文档第 4.2 节的实体关系图）。审计数据需要能够按会话标识完整回放，并支持完整性校验与证据包导出，以满足事后追溯与合规审查的需要。
