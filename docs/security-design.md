# 安全设计与威胁模型（security-design.md）

> 本文是项目安全叙事的「总纲」：先界定**威胁模型**（我们防什么、不防什么），
> 再给出贯穿全局的主线论点**「约束能力，而非检测内容」**，最后用一个工作示例
> （Dirty Frag 内核 LPE）把创新三件套（P1-1/2/3）串成一条完整论证。
> 能力到具体安全框架的逐条映射见 [security-mapping.md](./security-mapping.md)。

---

## 1. 一句话主张

> 对一个用自然语言驱动的运维 Agent，**真正的安全杠杆不在「把内容看得更准」，而在「把能力约束得更死」**。
> 能检测的威胁（危险命令、提示词注入）继续检测；不能检测的威胁（无害命令利用未知漏洞），
> 靠最小权限 + 沙箱遏制 + 时效化情报把**利用前提**物理移除。

这不是放弃检测，而是承认检测的边界，并补上正确的那条腿。

---

## 2. 威胁模型（防什么 / 不防什么）

我们把面对的威胁显式分成两类，对应两套应对：

### 威胁模型 A：运维操作安全（本护栏的主战场）
- **AI 推理不可控**：LLM 生成了误删库 / `chmod -R 777 /` / `mkfs` 等破坏性命令。
- **人为手滑**：用户授意但目标是关键路径（`/etc`、`/var/lib/mysql`、`/boot`）。
- **提示词注入**：对话或被读入的日志/文件内容里夹带「忽略之前规则」「你现在是 root」等诱导。
- **MCP 供应链**：工具元数据投毒 / 工具影子 / 隐形 Unicode 载荷。

应对（防线 1~4，均可演示、均有测试）：
| 防线 | 模块 | 作用 |
|---|---|---|
| 1 意图风险分类 | `guardrail/classifier.py` `risk_assessor.py` | 黑/灰/白分级 |
| 2 高危命令规则库 + 路径兜底 + AST | `guardrail/rules.py` `engine.py` `ast_analyzer.py` | 正则 + realpath/commonpath + Bash 语法树结构分析 |
| 3 提示词注入检测 / 数据-指令分离 | `guardrail/context_sanitizer.py` `taint`/`spotlighting` | 识别注入、外部内容打污点、不喂进决策流 |
| 4 最小权限 + 受控动作 + 执行沙箱 | `guardrail/privilege.py` `core/actions.py` `core/sandbox.py` | 非 root、二次确认、资源/能力保险丝 |

并以**致命三要素 / Rule of Two**（`guardrail/trifecta.py`）做结构性论证：15+ 个感知工具全 READONLY、
能力上限 ≤2 腿，第三条腿（改状态/外联）只存在于强制二次确认的动作层——任何可能集齐三要素的路径必经人工闸门。

### 威胁模型 B：系统沦陷（内容检测无法覆盖，本项目的创新延伸）
- **看似无害命令利用内核 0-day/N-day 提权**：工作示例 Dirty Frag（CVE-2026-43284 / 43500，2026-05 公开），
  经 `esp/rxrpc` 接口 + `splice` 操纵页缓存写，普通用户**用一串本身完全合法的命令**即可提权 root。

为什么防线 1~3 在这里**必然失效**：
1. **无内容特征**：利用过程的每条命令单看都合法，没有可供正则/AST 匹配的「危险模式」。
2. **知识库不实时**：模型训练截止在漏洞公开之前，模型根本不知道这个 CVE 存在。

→ 正确应对不是「更努力检测」，而是**遏制 + 时效化情报**（见第 3 节）。

### 明确不防（诚实标注，避免过度承诺）
- 不防物理访问 / 固件 / 供电侧攻击。
- 不防已被攻破的内核之上的取证对抗（一旦 root 沦陷，审计可信度边界即在此）。
- 姿态检查（P1-2）**不覆盖未披露 0-day**——没有情报无从比对；这类只能靠 P1-3 沙箱遏制兜底。
- 不做企业级身份体系（RBAC/SSO/OIDC）——竞赛单机场景用本机 token + 回环监听足矣（见 P0-4）。

## 3. 工作示例：用三件套应对 Dirty Frag

把 P1-1/2/3 串成一条针对威胁模型 B 的完整链路：

### P1-1 时效化情报：把「时效」从训练问题变检索问题
模型记不住新 CVE，但 Agent 可以**查**。`mcp_server/tools/vuln_intel.py` + 本地种子库
`app/data/advisories.json` 提供离线可检索的 advisory feed（含 Dirty Frag 受影响模块 `esp4/esp6/rxrpc`、
内核范围、缓解步骤），`live=True` 时联网 OSV.dev 增强、失败回退本地。
→ **架构上解决知识时效**：离线保证可演、联网保证可新、回退保证可靠。

### P1-2 姿态研判：把情报落到「本机此刻是否暴露」
`core/posture.py` 读本机内核版本 + `/proc/modules` 已加载模块，与情报比对：
> 「本机内核 6.x 命中 CVE-2026-43284（Dirty Frag），且 `esp4/rxrpc` 模块已加载 → 暴露。」

并给出**缓解候选**（`modprobe -r esp4 esp6 rxrpc` 或写 blacklist），但**绝不自动执行**——
须走 `/action/execute` 的护栏 + 二次确认（human-in-the-loop）。诚实标注：只覆盖已披露 N-day。

### P1-3 遏制：在「不认识漏洞」的前提下移除利用前提
Dirty Frag 的前提是「访问 esp/rxrpc 接口 + splice 操纵页缓存」。`core/sandbox.py` 把放行后真正落地的
命令丢进一个**削减了能力面**的 runner：
- 非 root（root 运行时 setuid 降权到 `opsagent`）；
- `prctl(no_new_privs)` + 从 capability bounding set 丢弃 `CAP_NET_ADMIN/NET_RAW/SYS_MODULE/SYS_PTRACE`；
- bwrap 路径再叠加 `--cap-drop ALL` + `--unshare-net/ipc/uts`。

→ 一个非 root、无 `CAP_NET_RAW/SYS_MODULE`、断网的进程，**打不开 raw/xfrm 套接字、加载不了模块**，
利用前提被物理移除。**关键**：这一遏制**不依赖认识 Dirty Frag**，故对**未披露 0-day 同样有效**。
（实测：非 root 下 `socket(AF_INET, SOCK_RAW)` 抛 `PermissionError`；子进程 `no_new_privs=1`。）

### 三件套的分工总结
| 件 | 回答的问题 | 对 0-day 是否有效 |
|---|---|---|
| P1-1 情报 | 这个**已披露**漏洞我知道吗？ | 否（需情报） |
| P1-2 姿态 | 本机此刻**是否暴露**于已披露漏洞？ | 否（需情报） |
| P1-3 遏制 | 就算被利用，**能不能成功**？ | **是**（不依赖认识漏洞） |

## 4. 推理可靠性：双通道，关键安全判断不依赖模型（正面回应「AI 推理不可控」）

赛题命门是「AI 推理不可控」。我们的回答是：**把关键安全判断从模型输出里剥离出来，做成确定性代码**，
让「模型不稳/被绕过/不可用」都不至于击穿安全。具体是**双通道 + 三层兜底**：

- **通道一：LLM 工具调用**（`deepseek` / 本地 `ollama`）——负责自然语言理解与工具选择（评分②），
  但其输出**不被信任**：选出的命令仍过护栏二次过滤。
- **通道二：确定性安全路由**——意图分类、注入检测、危险命令规则/AST、最小权限、致命三要素裁决
  **全部是确定性代码**（`guardrail/*`），不经模型；模型再怎么「推理不可控」，也改不了这些判定。

三层兜底保证「永远可演、永远有底」：
1. 云端 `deepseek`（开发/录屏默认，效果稳）；
2. 本地 `ollama`（答辩离线、国产化加分）；
3. `mock` 关键词路由（`llm/provider.py:MockProvider`，无 key 无网，CI 与「评委模式」演示走它）——
   **确定性 NL 路由**：磁盘/内存/进程/漏洞情报/内核姿态等需求都能在零依赖下选对工具走通闭环。

> 一句话：**LLM 决定「想做什么」，确定性护栏决定「能不能做」**。安全不押注在模型可靠性上——
> 这正是对「AI 推理不可控」最直接的工程化回答。（对应 OWASP LLM09 Overreliance，见 security-mapping.md。）

## 5. 命令护栏红队：发现并修补的绕过（诚实叙事 > 宣称 100%）

我们对自己的命令护栏做了红队，并把发现的绕过修补、固化为永不退化的回归测试
（`backend/tests/test_guardrail_bypass.py`）——**「发现并修补 N 类基础绕过」比「宣称 100% 通过」更可信**，
这与第三方测试的诚实叙事一致，是公信力的提升而非减分。

**发现**：早期护栏对「解释器 + 内联代码」整串正则失配——`bash -c "rm -rf /"` 里 `rm -rf /` 是引号字符串、
DEL-001 的 `/(\s|$)` 因 `/"` 收尾而漏判，bashlex 也不会去解析 `-c` 后那段（内层可为任意语言、内容无界）。
而 executor 用 `shlex.split + shell=False`，argv `['bash','-c','rm -rf /']` 执行时**真的会跑**——是真实绕过。
实测 8 条样例里 7 条以 LOW/ALLOW 通过（`bash -c`、`sh -c`、`python3 -c`、`find / -delete`、
`find / -maxdepth 1 -delete`、`truncate -s 0 /etc/passwd`、`kill -9 1`）。

**修补（结构性，不走黑名单跑步机）**：
1. **把包装结构本身当信号**：「解释器 + 内联代码」这一**结构事实**判 CRITICAL/DENY——刻意**不解析内层**
   （内层语言不定、内容无界，静态无法可信审查）。这正是「约束能力，而非检测内容」在命令层的落地。
2. **realpath 路径兜底从「只管 rm」推广到不可逆数据销毁动词**（rm/unlink/shred/truncate/tee/dd/mkfs/find-delete），
   凡操作数规范化后落在关键路径即 CRITICAL；变量化/相对/软链变形也兜得住。
3. **kill PID 1/-1 红线**。
   （有判断地**不**把可恢复的 chmod/chown 升 CRITICAL：危险变形已由 PERM-* 覆盖，盲升会误杀常规运维、
   破坏「误杀率 0%」——见 dev-log。）
4. **执行层补刀：executor argv 原生化**。绕过的物理根源是「executor 把命令当字符串、执行前再 `shlex.split`」。
   新增结构化入口 `execute_argv(argv: list[str])`：argv 即权威执行对象，护栏在 `shlex.join(argv)` 上裁决、
   放行后**直接执行该 argv 不再二次解析**。因 `shlex.split(shlex.join(x)) == x` 对良构 argv 恒等，**「护栏所审
   字符串」与「真正执行的 argv」可证同源**——受控变更路径（kill/clean，唯一真实生产路径）从根上消除「拼接→再
   解析」面。原 `execute(str)` 保留为自由形态/兼容入口，仍靠规则库 + AST 兜（见 dev-log「P0-A.4」）。

**两条结构性论点（答辩金句）**：
- **解释器内联代码无法静态可信审查 → 把包装结构本身当信号**（而非徒劳地去读内层）。
- **命令护栏总会被新变形绕过 → 非 root 受限沙箱（§3 P1-3）兜底爆炸半径**。检测能挡的继续挡，
  挡不住的由「约束能力」在 OS 层物理收口。一套「约束能力而非检测内容」的哲学，贯穿**命令绕过、内核漏洞、
  提示注入**三类威胁。

> 结果：原始 7 条 + 27 条变形全部不再 LOW/ALLOW，19 条正常/同形安全命令零误杀（误杀率仍 0%）。

### 5.1 第三方范式独立红队：注入维度也照此修补（RedCode-Exec / DeepTeam）

把「自评安全」升级为「对抗语料独立打分」：`scripts/redteam_eval.py` 是 RedCode-Exec（风险代码该不该
被允许执行）与 DeepTeam（注入/越狱该不该被识破）两类基准的**本地化离线评测器**——护栏即被测目标，
危险命令走 `check_command`、注入话术走 `scan_injection`，按家族算检出率 / 攻击成功率(ASR) / 误拦率。

**首跑如实暴露的盲区**（诚实叙事的又一次兑现）：命令护栏 18/18 全拦、良性命令/诉求 0 误拦，但
**防线3 的注入检出仅 30%**——7 条 DeepTeam 风格越狱从规则缝里漏过：DAN/unrestricted「无限制人格」、
「输出你的系统提示词」、「disregard the safety **policy**」（原规则只认 rule/instruction）、对话内夹带
`<important>…</important>` 隐藏指令、「pretend the rules don't apply」、「system override … without
confirmation」。

**修补（结构性扩面，非个案打补丁）**：在可热加载的 `rules.yaml` 增 INJ-006~010 五类注入规则——套取系统
提示词 / 声称安全规则不适用 / 无限制越狱人格 / 关闭护栏免确认 / 隐藏指令伪标签，并把 INJ-001 的指令覆盖
扩到 policy/guardrail。复跑 **42/42、ASR 0%、误拦 0%**；7 条越狱语料并入 `test_guardrail_redteam.py` 的
INJECTIONS 固化为**永不退化回归**。`scan_injection` 与 `classify_intent` 同源复用 inject 规则，故同一次扩面
既提升注入检出、又让这些话术被意图分类判「黑」直接拒绝、不进 LLM。

> 一以贯之：**发现并修补 N 类绕过 > 宣称 100%**。命令维度（§5）与注入维度（§5.1）两次都按同一方法论——
> 用对抗评测找洞、结构性扩面修补、固化回归——这比任何「全部通过」的断言都更有公信力。

## 6. 已知边界与未来工作

- **运行时行为检测（eBPF / auditd / Falco）**：当前不引入（竞赛虚机跑不动，且属重型 IDS）；
  作为「遏制之后再加一层观测」的未来工作列出。
- **0-day 情报的实时性**：本地 feed 需人工/定时更新；live fetch 仅按需触发，未做后台轮询。
- **沙箱强度**：纯 rlimit 兜底无法做完整 seccomp 系统调用过滤；完整 socket 族 / syscall 过滤依赖 bwrap/nsjail
  或后续 seccomp-bpf（列为未来工作）。
- **审计可信边界**：HMAC 哈希链防的是「事后篡改日志」；一旦内核 root 沦陷，运行中的审计进程本身不可再被信任。

> 设计原则一以贯之：**不执行任意 shell**、变更走受控 action、默认只读、高危需人工确认、本地模型有确定性 fallback。

## 7. 测量学诚实声明（第二轮评审整改）

第二轮评审指出测试体系有三处「看着满分、实则口径不客观」之处。如实记录并已整改：

### 7.1 命令护栏的路径裁决依赖**宿主机真实文件系统**

`hits_critical_path` 与 `effect_analyzer` 用 `os.path.realpath` 把命令里的路径规范化后再判是否落在
关键区——这是看穿「相对路径 / 软链接绕过」的必要手段，但也意味着**裁决与运行时文件系统状态耦合**：
同一条命令在软链布局不同的两台主机上，理论上可能得到不同裁决；红队 / CI 跑出的分数隐含「靶机
此刻的 FS 状态」这一前提。这是 realpath 兜底的固有代价（去掉它则软链绕过重现），权衡后保留，但
**封存声明里据此补一句**：held-out 的字节封存保证「卷子没变」，不保证「评测主机 FS 状态恒定」——
所以分数应理解为「在标准麒麟靶机基线 FS 上」的结果，换机复现需同基线。

### 7.2 自由形态 `executor.execute(str)` 是**纵深防御层**，不是攻击者可达路径（叙事纠偏）

红队语料把命令串喂给 `execute(..., dry_run=True)` 量护栏强度——这对验证「规则 + AST + 效果」这层
**确定性兜底**是对的，但要避免把「100% 拦截 RedCode-Exec」误读成「端到端攻击零成功」。事实是：
**产品里 LLM 根本到不了 `execute(str)` 这个自由形态入口**——编排路径只让模型从 READONLY MCP 工具里
**选**工具，变更只有用户经 `/action/execute` 触发的 3 个参数化动作（走 `execute_argv`）。自由字符串入口
仅存在于「测试 / 红队脚本 / `/guardrail/check` 只读预览」。所以：

> **真正的第一道防御是架构（LLM 够不到危险路径），红队分数量的是它之下的规则兜底层。** 两者都要，
> 但讲故事时架构是主角、规则是配角——见 §4 与 trifecta 不变量。

### 7.3 评分② 真模型基准 + ASR 去噪 + 良性扩面（三项已补齐）

- **② 自然语言准确性此前只有 mock 测试**（关键词路由，测的是管道不是模型）。新增
  `scripts/nl_eval.py` + 带标准答案的 `scripts/corpora/nl_intent_eval.jsonl`，驱动**真 Orchestrator +
  真 MCP + 真 LLM** 度量「一句话→选对工具」top-1 准确率，报告见 `docs/nl-accuracy-report.md`
  （记录 provider/model/时间戳，未命中用例如实列出；mock 跑出的分会被显式标注为「不代表②」）。
- **ASR 去噪**：`redteam_eval` 把攻击家族「漏过」按效果二分为 `real_miss`（真盲区）与
  `corpus_benign`（外部语料把世界可读的无害读错标为攻击），并给出剔噪后的**真·ASR**。于是
  v5 held-out 从「ASR 5%」诚实拆成「原始 5% / 真·0%，2 条 `/proc/cpuinfo`·`openssl.cnf` 读系语料错标」。
- **良性语料扩面**：误杀率对照从 17 例扩到 54 例（只读关键区 / 非关键路径写删 / 备份 / 下载落 tmp 等
  「看着吓人实则常规」运维）。扩面当场逼出并修掉一个**真误杀 bug**——防线4 的 `\bpasswd\b` 正则命中
  路径 `/etc/passwd` 子串，把 `stat /etc/passwd` 误判为「改口令、需 root」拦下；已改为命令位锚定。

### 7.4 意图层不做明文关键词过滤：明文匹配在输入侧本质可绕（架构纠偏）

第二轮整改还暴露了一处**方向性**问题：防线1 曾用明文关键词在**意图层**对「破坏意图」判黑
（`格式化磁盘`、`删整个系统`、`关防火墙`、`提权/后门`）。这条做法经评审被判定为**应当移除**，理由有二：

1. **对真实攻击≈摆设。** 明文关键词过滤打在**输入侧自然语言**上，而绕过它的方法是无穷的——
   base64 / hex 编码、小语种（低资源语言越狱）、同义改写，乃至针对开源模型用 GCG 生成的对抗性后缀。
   任何一条恶意意图都有无数种不触发明文过滤器的表述。**把它当安全控制，是给一面早已是混凝土的墙刷涂料。**
2. **对正常用户高频误杀。** 「提权 / 后门 / 格式化 / 清理」恰是安全运维的**日常词汇**。实测：
   「帮我检查下有没有 Dirty Pipe 那类提权风险」——一句正当的防御性排查——被裸词 `提权` 判黑拦在门口
   （评分② 真模型基准 `nl_eval` 当场暴露）。话题词不是动作，不该上意图黑名单。

**关键认识：那个关键词从来就不是挡在攻击者与破坏之间的那道墙。** 本架构里**根本不存在
「自然语言 → 任意命令执行」这条路**——LLM 只能【选只读 MCP 工具】+【3 个强制二次确认的白名单动作】，
攻击者把恶意命令用 base64+小语种+GCG 包装到天上、把 LLM 彻底越狱，它手里也没有能格式化磁盘/提权的
工具腿，**炸不了系统**。安全边界由三层确定性机制保证，没有一层依赖意图层的话术匹配：

| 层 | 作用对象 | 为何不惧 base64/小语种/GCG |
|---|---|---|
| 架构 | 能力面（工具只读 + 动作白名单） | 无任意执行腿，越狱再成功也无危险能力可调用 |
| 防线1.5 | 灰意图的 LLM **语义**研判 | 委婉删库「把没用的大家伙清理掉」这种【无关键词可匹配】的才是真考验，靠语义非话术（真机实测 → critical/deny） |
| 防线2 | **已被模型解码成的具体命令产物** | 混淆到产物侧早被「编译掉」——无论用户用英文/小语种/base64 问，落地的都是明文 `mkfs`/`rm -rf /`，realpath+AST+效果分析在此才有牙 |

**整改动作**：移除防线1 全部破坏意图的明文判黑（含连带的脆弱「诊断 vs 动作」正则），`classify_intent`
降格为纯**路由层**（白=只读快路 / 灰=进 防线1.5+命令级护栏）。**唯一保留的 BLACK 是注入/操纵话术**——
但它也不是安全承重（真正抗注入是 防线3 `scan_injection` 的结构化隔离 + 上述架构，orchestrator 另有
`scan_injection` 独立兜底），仅作一道廉价、低误报的「拒绝与操纵对话 + 留审计」首过滤。

> 一句话叙事：**意图层是路由不是闸门。** 这与 §4「黑名单跑步机永远追不完，只有架构保证是确定性的」
> 一脉相承——把明文匹配从「冒充安全」纠正回「辅助路由」，既消除误杀，也不丢任何真实防护。
