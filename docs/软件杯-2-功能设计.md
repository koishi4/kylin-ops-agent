**项目名称**：面向麒麟操作系统的安全智能运维 Agent
**赛题编号**：中国软件杯 A2
**文档版本**：v1.0

---

## 1 引言

### 1.1 编写目的

本文档在需求分析的基础上，给出系统的总体设计与详细设计，包括架构、模块划分、类设计、关键流程时序、数据库与接口设计、部署与构件设计，作为编码与测试的直接依据。

### 1.2 设计指导思想

本项目的第一安全保证**不是**「拦住 LLM 生成的危险命令」，而是**从架构上让 LLM 根本没有生成自由命令的途径**（Action-Selector / 能力受限范式）：

- **感知/查询路径**：LLM 只能从 READONLY MCP 工具里「选工具」，不能拼装、不能自由执行；不可信工具输出经 CaMeL 双 LLM 隔离后才回喂规划器。
- **变更/处置路径**：只有 7 个白名单参数化动作，且只能由用户经 `/action/execute` 显式触发、强制二次确认；LLM 无法把它们当工具调用（不在 MCP 注册表里）。

由此得到结构性不变量：全部 MCP 工具均为 READONLY、无「改状态/外联」能力腿，注入再成功也无法升级为状态变更；变更入口与 LLM 编排路径物理隔离。命令规则引擎是这条架构之上的**纵深防御**。

## 2 总体设计

### 2.1 设计目标与原则

| 原则 | 落地 |
|---|---|
| 安全护栏为灵魂 | 四道防线 + 架构隔离 + CaMeL 信息流控制 |
| 统一执行出口 | 所有可变命令必经 `core/executor.py`，护栏不放行不执行 |
| 最小权限 | 非必要不 root；受控动作沙箱降权落地 |
| 全链路可追溯 | 五段思维链 + HMAC 哈希链审计 |
| 插件化可扩展 | MCP 工具注册表 + 规则库热加载 + 白名单动作可增 |
| 国产化 | DeepSeek 国产开源大模型 + 麒麟/LoongArch 部署 |

### 2.3 模块划分

系统划分为五大核心模块（远超课程报告「模块数≥4」要求）：

| 模块 | 目录 | 职责 | 对应评分子项 |

## 3 详细设计

### 3.1 安全护栏设计（项目灵魂）

#### 3.1.1 四道防线总览

```
自然语言 ─→ 编排器 ─┬─ 防线1   意图分类（路由层：白只读快路 / 灰进研判）
                     ├─ 防线1.5 LLM 语义研判（对灰意图叠加，与规则保守合并取更严）
                     └─ 防线3   提示词注入检测（用户输入 + 工具输出沙盒化）

候选命令 ─→ executor 统一出口 ─┬─ 防线2 高危命令规则库
                                │       （正则 + realpath 路径兜底 + Bash AST + 副作用效果分析，
                                │        四者保守合并、只升不降）
                                └─ 防线4 最小权限校验（非必要不 root）
```

#### 3.1.2 规则库设计

规则以 `Rule(id, pattern, risk, action, description, category)` 数据类表达，覆盖六类：删除、权限、磁盘、提权、配置、注入；外加外联/反弹 shell（egress）。风险分级 `RiskLevel ∈ {CRITICAL, HIGH, MEDIUM, LOW}`，门控动作 `Action ∈ {DENY, CONFIRM, ALLOW}`。规则存于 `rules.yaml`（36 条，支持热加载），红线规则（CRITICAL+DENY）硬编码于 `rules.py` 兜底，配置层无法削弱。

裁决采用**保守合并取更严**：正则、realpath 路径兜底、Bash AST 结构分析、副作用效果分析四者的命中并入同一 `hits`，风险标签取最高、门控取 DENY/CONFIRM 并集，逐一兑现，只升不降。命令裁决的状态机如图 4.5 所示。

![护栏裁决状态机](uml/state-verdict.png)

<p align="center">图 4.5　护栏命令裁决状态机（防线2 + 防线4）</p>

#### 3.1.3 抗注入与 CaMeL 信息流隔离

- **入口注入**：用户输入经 `scan_injection` 结构化检测，命中即拒绝并留痕；
- **工具输出注入**：工具返回视为外部不可信数据，先 `sanitize_tool_result`（spotlighting/datamarking 打标）；不可信或检出注入的输出经 `_quarantined_read`——一次**无工具**的隔离阅读器调用，把原始字节压成被重新标记为不可信的摘要后才回喂规划器；
- **污点门控**：路径一旦摄入不可信数据即标记 `tainted`，配合能力面评估强制「污点 ∧ 状态变更 恒不成立」不变量。

### 3.2 MCP 工具层设计

23 个工具全部 READONLY，按六大类封装，集中登记于 `REGISTRY: dict[str, ToolSpec]`，由 `server.py` 统一注册到 FastMCP。

| 类别 | 工具 |
|---|---|
| 磁盘 | disk_usage、find_large_files、dir_size、inode_usage |
| 内存/系统 | memory_info、system_load、uptime_info、service_status、list_failed_units |
| 进程 | list_processes、find_zombie_processes、process_detail |
| 网络 | list_listening_ports、check_port、firewall_status |
| 日志 | tail_log、query_journal |
| 句柄 | list_open_files |
| 安全态势 | login_history、list_cron_jobs、query_vuln_intel、kernel_posture |

每个工具是一个纯函数（便于 pytest），返回结构化 dict，标注 `level`。真正的可变动作不进此表。

### 3.3 受控动作层设计

7 个白名单参数化动作，统一经 `run_action` 分发，每个动作「语义校验 → 结构化 argv → executor 护栏 → 强制二次确认 → 五段审计」。

| 动作 | 落地方式 | 语义闸门 |
|---|---|---|
| truncate_log | fd-safe `os.ftruncate`（O_NOFOLLOW 防软链写穿） | 仅 CLEANABLE 类、拒符号链接、消除 TOCTOU |
| kill_process | `kill -SIG pid`（结构化 argv） | 禁 init/systemd/自身/关键服务；root 进程需授权；信号白名单 |
| clean_path | `rm -f path` | 仅 CLEANABLE、仅普通文件；命令仍过 PATH-001 兜底 |
| restart_service | `systemctl restart unit` | unit 白名单校验、关键单元拒、需显式授权 |
| reload_config | `systemctl reload unit` | 同上 |
| block_ip | `iptables -I INPUT -s ip -j DROP` | 拒网段/特殊地址/当前 SSH 来源（防自锁）、需授权 |
| clean_journal | `journalctl --vacuum-size/--vacuum-time` | size/time 二选一且格式白名单 |

**扩展实用性的正确方向**：往白名单加参数化受控动作（每个都过语义闸门 + 二次确认 + executor 护栏），而非给 LLM 自由 shell。

### 3.4 执行器设计

`executor` 是所有可变命令的唯一出口，提供两个入口：

- `execute(cmd: str)`：自由形态字符串，护栏在原始字符串上裁决；
- `execute_argv(argv: list[str])`：结构化入口（受控动作首选），`argv` 即权威执行对象，护栏在 `shlex.join(argv)` 上裁决，「所审即所执」可证，消除「字符串→argv」再解析的歧义。

放行后套轻量沙箱（资源/权限限额）落地，即便护栏误放行也炸不了宿主机。

### 3.5 根因分析设计

`diagnosis` 消费 MCP 只读数据做「推理 + 关键性判断 + 建议」，**绝不执行**任何处置：

- 磁盘满 → 定位大文件 → `classify_file` 判关键性（`FileClass ∈ {CLEANABLE, CRITICAL, UNKNOWN}`）→ 给清理建议；
- 僵尸进程 → 定位父进程（回收靠父进程）；
- 负载/内存/IO → 过载判断 + 占用最高进程；内存泄漏（RSS 增长 + swap 颠簸）证据链；
- 配置漂移 → TOFU 锚定关键配置基线，报告 changed/removed/added。

## 4 接口设计

### 4.1 REST API 接口

| 方法 | 路径 | 功能 | 鉴权 |
|---|---|---|---|
| GET | `/health` | 健康检查 + 当前 LLM provider | 否 |
| GET | `/tools` | 列出 MCP 工具（评分①可演示） | 否 |
| POST | `/chat` | 自然语言运维对话，返回 answer + trace | 否 |
| GET | `/guardrail/rules` | 列护栏规则库（评分③可视化） | 否 |
| POST | `/guardrail/rules/reload` | 规则热加载 | operator |
| POST | `/guardrail/check` | 对单条命令做护栏裁决（拦截 demo） | 否 |
| GET | `/guardrail/trifecta` | 能力面板（Rule of Two） | 否 |
| GET | `/guardrail/tool-scan` | MCP 工具供应链扫描 | 否 |
| GET | `/diagnose` | 智能根因分析（评分④） | operator |
| POST | `/action/execute` | 受控动作端到端（唯一改状态入口） | operator |
| GET | `/traces` | 最近会话列表 | 否 |
| GET | `/traces/{id}` | 按 trace_id 取完整五段 | 否 |
| GET | `/traces/{id}/verify` | 校验哈希链完整性 | 否 |
| GET | `/traces/{id}/evidence` | 导出自封口审计证据包 | operator |

`/action/execute` 请求体：`{action, params, confirmed, authorized, dry_run}`；动作名用 Literal 收敛到白名单，未知动作入口即 422。
