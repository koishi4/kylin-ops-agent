# 软件性能（核心指标）测试报告

**项目名称**：面向麒麟操作系统的安全智能运维 Agent
**赛题编号**：中国软件杯 A2
**文档版本**：v1.0

---

## 1 测试概述

### 1.1 测试目的

量化系统核心性能指标，重点回答两个问题：① 安全护栏是否会拖慢运维（护栏开销）；② 一次自然语言对话的端到端延迟由什么主导。

### 1.2 测试方法

性能数据由 `python scripts/bench.py` 自动生成（不手改），对护栏裁决、注入扫描、意图分类、根因推理做单次延迟采样与批量吞吐测量；端到端延迟用 mock LLM 隔离本地开销，再叠加真实 DeepSeek 往返区间估算。

### 1.3 测试环境

| 项 | 配置 |
|---|---|
| Python | 3.11.15 |
| 平台 | Linux x86_64 |
| CPU 核数 | 32 |
| 内存 | 16.6 GB |
| 采样时间 | 2026-06-10 |

## 2 护栏与推理延迟（单次调用）

| 指标项 | 采样次数 | 均值(μs) | P50(μs) | P95(μs) | P99(μs) |
|---|--:|--:|--:|--:|--:|
| 护栏命令裁决（防线2+4） | 300 | 229.3 | 214.7 | 378.0 | 471.2 |
| 注入扫描（防线3） | 300 | 30.5 | 32.5 | 41.8 | 51.4 |
| 意图分类（防线1） | 300 | 25.6 | 24.2 | 39.6 | 49.2 |
| 跨信号关联根因推理（评分④） | 300 | 61.3 | 54.3 | 92.1 | 167.3 |

> 结论：护栏裁决在**数十至数百微秒（亚毫秒）量级**，相对一次运维操作可忽略——「安全护栏不拖慢运维」有量化支撑。

## 3 批量裁决吞吐

累计裁决 **3550** 条命令，耗时 **849.4 ms**，吞吐 **4,180 decisions/s**。

## 4 端到端一次对话延迟（拆解）

> 用户感知延迟由 **LLM 往返**主导（秒级），护栏/工具仅毫秒级，两者差 3~4 个数量级。

**毫秒级本地段（mock LLM，把 LLM 往返置零）**

| 阶段 | 耗时 | 说明 |
|---|--:|---|
| 单次 MCP 工具调用 | 1.0 ms | 真实读取系统数据（disk_usage） |
| 本地段合计 | 18.2 ms | 护栏 + 工具 + 编排 + 审计，LLM 段≈0 |

**主导项：串行 LLM 往返次数（按意图分类）**

| 意图类 | 串行 LLM 往返 | 单次查询墙钟估算※ |
|---|--:|--:|
| 白（只读查询） | 2 (+R) | ~12–24 s |
| 灰（修改/动作） | 3 (+R) | ~18–36 s |
| 直接作答（无需工具） | 白1 / 灰2 | ~6–24 s |

※ 按单次 LLM 往返 ~6–12 s（真实 DeepSeek 实测区间）× 往返次数估算；(+R) 为读到不可信工具输出时多一次 CaMeL 隔离阅读器往返。

> 拆解结论：① 端到端延迟 ≈ 往返次数 × 单次 LLM 耗时，由模型主导；② 灰意图为换取「规则保可靠 + LLM 补泛化」的双层安全研判刻意多付一次串行往返，是安全与时延的自觉取舍；③ 优化杠杆在 LLM 侧（缓存、换更快/本地小模型、并发只读工具），而非已可忽略的护栏开销。

## 5 性能结论

| 核心指标 | 数值 | 评价 |
|---|---|---|
| 护栏单次裁决均值 | 229.3 μs | 亚毫秒，对运维无感知影响 |
| 护栏裁决吞吐 | 4,180 次/秒 | 高吞吐，不构成瓶颈 |
| 本地段合计 | 18.2 ms | 护栏+工具+编排+审计总开销极低 |
| 端到端延迟主导项 | LLM 往返（秒级） | 由模型决定，护栏占比可忽略 |

安全护栏在带来 100% 危险拦截能力的同时，仅引入亚毫秒级开销，**安全性与性能不矛盾**。
